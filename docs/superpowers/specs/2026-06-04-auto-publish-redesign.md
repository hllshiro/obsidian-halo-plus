# 自动发布机制重新设计

## 概述

将自动发布机制从"事件触发型"重构为"状态感知型"，核心思想是：**发布不是事件，而是状态**。系统感知内容何时进入稳定态，而非响应每次保存事件。

## 设计目标

1. **减少发布次数**：避免频繁小修改导致的多次发布
2. **降低发布延迟**：内容稳定后及时发布，不等待固定时间
3. **符合写作习惯**：感知"写作阶段结束"而非"文件保存"
4. **保留手动发布**：不影响现有手动发布功能

## 核心概念

### Publish Intent（发布意图）

内部概念，表示当前内容有多大概率已经完成。由三个维度构成：

1. **Activity（活跃度）**：用户是否还在持续编辑
2. **Session End Signal（会话结束信号）**：是否切文件、失焦等
3. **Change Magnitude（修改规模）**：本轮改动大小

### Stable State（稳定态）

当 Publish Intent 超过阈值时，认为内容进入稳定态，可以发布。

## 架构设计

### 整体流程

```
内容修改
   ↓
  DIRTY（标记文件为脏）
   ↓
持续计算稳定分数：
  - 活跃度 (Activity)
  - 会话结束信号 (Session)
  - 修改规模 (Change)
   ↓
分数超过阈值
   ↓
进入 READY 状态
   ↓
观察窗口（15秒）
   ↓
Hash 未变化
   ↓
发布
   ↓
冷却期（5分钟）
```

### 核心组件

| 组件 | 职责 |
|------|------|
| `AutoPublishManager` | 主控制器，管理整个自动发布生命周期 |
| `StableScoreCalculator` | 计算稳定分数 |
| `EventMonitor` | 监听 Obsidian 事件并更新状态 |
| `PublishQueue` | 发布队列，处理冷却和去重 |

### 状态机设计

每个文件的状态转换：

```
IDLE → DIRTY → READY → PUBLISHING → COOLDOWN
  ↑                                    ↓
  └────────────────────────────────────┘
```

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| `IDLE` | 无修改，空闲 | 初始状态或冷却期结束 |
| `DIRTY` | 有修改，计算稳定分数 | 收到编辑事件 |
| `READY` | 分数达标，进入观察窗口 | 稳定分数 ≥ 阈值 |
| `PUBLISHING` | 正在发布 | 观察窗口结束且内容未变 |
| `COOLDOWN` | 冷却期 | 发布成功 |

**状态转换规则：**
- `IDLE → DIRTY`：收到编辑事件
- `DIRTY → READY`：稳定分数达到阈值
- `DIRTY → DIRTY`：收到新编辑事件，重置计时器
- `READY → PUBLISHING`：观察窗口结束且内容未变
- `READY → DIRTY`：观察窗口期间内容变化
- `PUBLISHING → COOLDOWN`：发布成功
- `COOLDOWN → IDLE`：冷却期结束

## 事件监听设计

### 监听的事件

| Obsidian 事件 | 用途 | 更新的分数 |
|---------------|------|-----------|
| `editor-change` | 检测编辑活动 | Activity（重置） |
| `active-leaf-change` | 检测文件切换 | Session（+80） |
| `window blur` | 检测窗口失焦 | Session（+60） |
| `vault.modify` | 检测文件保存 | Change（计算 diff） |
| `quit` | 应用退出 | 触发退出时发布 |

### 实现方式

在 `AutoPublishManager` 中统一注册事件，事件触发时更新对应文件的状态和分数。使用 `Map<string, FileState>` 管理每个文件的状态。

## 稳定分数计算

### 分数公式

```
Score = ActivityScore + SessionScore + ChangeScore
```

### 各维度分数

| 维度 | 条件 | 分数 |
|------|------|------|
| Activity | 最近 10 秒有输入 | 0 |
| Activity | 最近 1 分钟无输入 | +20 |
| Activity | 最近 5 分钟无输入 | +60 |
| Session | 文件切换 | +80 |
| Session | 窗口失焦 | +60 |
| Change | 修改 < 10 字符 | +10 |
| Change | 修改 10-100 字符 | +30 |
| Change | 修改 > 100 字符 | +50 |

### 阈值

默认阈值：100 分（可配置）

## 发布流程

### 正常发布流程

1. 文件进入 `DIRTY` 状态
2. 每次事件更新分数
3. 分数 ≥ 100 → 进入 `READY` 状态
4. 启动 15 秒观察窗口（可配置）
5. 观察窗口期间：
   - 如果内容变化 → 回到 `DIRTY`，重置
   - 如果内容不变 → 继续等待
6. 观察窗口结束 → 计算内容 Hash
7. Hash 与上次发布相同 → 跳过
8. Hash 不同 → 进入 `PUBLISHING`，执行发布
9. 发布成功 → 进入 `COOLDOWN`（5 分钟）
10. 冷却期结束 → 回到 `IDLE`

### 退出时发布流程

1. 监听 `quit` 事件
2. 检查所有标记为 dirty 的文件
3. 跳过观察窗口和冷却期
4. 直接发布所有 dirty 文件
5. 设置 30 秒超时，超时后放弃并关闭

## 配置项设计

### 设置结构

```typescript
interface AutoPublishSettings {
  enabled: boolean;           // 启用自动发布
  folders: string[];          // 监听的文件夹
  idleTimeout: number;        // 空闲超时（秒），默认 300
  stableThreshold: number;    // 稳定分数阈值，默认 100
  observationWindow: number;  // 观察窗口（秒），默认 15
  cooldownTime: number;       // 冷却时间（秒），默认 300
  publishOnQuit: boolean;     // 退出时发布，默认 true
  quitTimeout: number;        // 退出超时（秒），默认 30
}
```

### 设置界面

- **基础设置**：启用/禁用、监听文件夹
- **高级设置**（折叠面板）：所有时间参数

## 边界情况处理

### 1. 快速连续编辑

- 每次编辑重置 Activity 计时器
- 累积 Change 分数
- 避免频繁状态转换

### 2. 多文件同时编辑

- 每个文件独立状态机
- 独立计算稳定分数
- 独立发布队列

### 3. 网络异常

- 发布失败不进入冷却期
- 保留 DIRTY 状态，等待重试
- 记录错误日志

### 4. 应用崩溃

- 状态不持久化，重启后重新开始
- 内容 Hash 机制避免重复发布

### 5. 应用退出

- 监听 `quit` 事件
- 跳过观察窗口，直接发布
- 设置超时保护

## 性能考虑

1. **事件节流**：`editor-change` 事件需要节流，避免过于频繁的计算
2. **延迟计算**：稳定分数计算使用延迟任务，避免阻塞 UI
3. **内存管理**：清理长时间不活跃的文件状态
4. **批量发布**：退出时的发布可以批量处理

## 可观测性
