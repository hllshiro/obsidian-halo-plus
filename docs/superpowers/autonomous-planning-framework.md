# 自主规划框架

## 概述

本框架定义了在用户指出开发方向和问题时，如何自主规划实现方案、提交代码和发版的流程。

## 响应流程

### 1. 接收用户输入

用户输入可能包括：
- 开发方向（如"添加功能X"、"优化性能"）
- 问题描述（如"发布时图片上传失败"）
- 改进建议（如"UI交互需要优化"）

### 2. 分析与评估

#### 2.1 问题分析
- 明确问题范围和影响
- 确定涉及的功能模块
- 评估技术复杂度

#### 2.2 优先级评估
- **高优先级**：影响核心功能、用户体验严重受损
- **中优先级**：功能改进、性能优化
- **低优先级**：代码质量、文档完善

### 3. 制定实现计划

#### 3.1 设计阶段
- 创建设计文档（`docs/superpowers/specs/`）
- 定义技术方案和架构
- 确定涉及的文件和模块

#### 3.2 实现阶段
- 创建实现计划（`docs/superpowers/plans/`）
- 分解为具体任务
- 定义验证标准

### 4. 代码提交策略

#### 4.1 提交时机
- **立即提交**：修复关键bug、安全漏洞
- **功能完成后提交**：新功能开发完成并通过测试
- **批量提交**：相关的小改进可以合并提交

#### 4.2 提交规范
- 遵循 Conventional Commits 规范
- 提交信息清晰描述变更内容
- 关联相关的issue或需求

### 5. 发版策略

#### 5.1 发版时机
- **补丁版本**（0.0.x）：bug修复、小改进
- **次版本**（0.x.0）：新功能、非破坏性改进
- **主版本**（x.0.0）：重大变更、破坏性更新

#### 5.2 发版流程
1. 更新版本号（package.json, manifest.json）
2. 更新CHANGELOG.md
3. 创建git tag
4. 推送到远程仓库

## 决策矩阵

| 变更类型 | 提交时机 | 版本类型 | 示例 |
|---------|---------|---------|------|
| 关键bug修复 | 立即 | 补丁版本 | 发布功能完全失效 |
| 新功能 | 功能完成后 | 次版本 | 添加图片上传功能 |
| 性能优化 | 优化完成后 | 补丁版本 | 渲染性能提升 |
| UI改进 | 改进完成后 | 补丁版本 | 交互体验优化 |
| 重构 | 重构完成后 | 次版本 | 代码结构调整 |
| 重大架构变更 | 变更完成后 | 主版本 | API接口重设计 |

## 工具与脚本

### 版本发布
```bash
# 发布新版本
node scripts/release.js <version>

# 示例
node scripts/release.js 0.5.1
```

### 代码质量检查
```bash
# lint检查
pnpm lint

# 自动修复
pnpm lint:fix

# 构建验证
pnpm build
```

## 注意事项

1. **保持向后兼容**：尽量避免破坏性变更
2. **充分测试**：确保变更不会引入新问题
3. **文档更新**：及时更新相关文档
4. **用户沟通**：重大变更前与用户确认

## 示例场景

### 场景1：用户报告bug
**用户输入**："发布时图片上传失败"

**响应流程**：
1. 分析问题：图片上传模块异常
2. 制定计划：检查上传逻辑、错误处理
3. 实现修复：修复上传代码
4. 提交代码：`fix(upload): 修复图片上传失败问题`
5. 发版决策：补丁版本（0.5.1）

### 场景2：用户提出新功能
**用户输入**："希望支持批量发布"

**响应流程**：
1. 分析需求：批量操作功能
2. 设计方案：UI设计、数据结构
3. 实现功能：批量选择、发布逻辑
4. 提交代码：`feat(publish): 支持批量发布功能`
5. 发版决策：次版本（0.6.0）

### 场景3：用户指出性能问题
**用户输入**："大量笔记时渲染很慢"

**响应流程**：
1. 分析性能瓶颈
2. 制定优化方案
3. 实现性能优化
4. 提交代码：`perf(renderer): 优化大量笔记的渲染性能`
5. 发版决策：补丁版本（0.5.1）
